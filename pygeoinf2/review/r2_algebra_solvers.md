## 2. Bugs and regressions found now

**Verified**

1. **`LUSolver` factorises twice at construction.** solvers.py:398 `_factorise` → `lu_factor`; :409 `_factorise_transposed` → `lu_factor` again (:461). Repro (prof1): dim 1500 → 2 `lu_factor` calls, build 91 ms vs 47 ms for one; ratio 1.93. v1 factorised once and used `trans=1` (linear_solvers.py:117-126) — a regression introduced by the fix for S Should-12. test_solvers.py:413 counts *applications*, not factorisations, so it cannot see this. Fix: factor once in `_invert` and derive both closures from it. Results are correct (adjoint to 2e-13 on `make_dense_metric_space(60)`).
2. **`from_formal_adjoint` over a `MassWeightedSpace` fails for an equal-but-distinct base.** `MassWeightedSpace.shares_vectors_with` (spaces.py:683) tests `other is self._base`; `_transfer` (operators.py:161-168) then raises. Repro (metric_checks): `E = EuclideanSpace(3); MW = MassWeightedSpace(E, M); LinearOperator.from_formal_adjoint(MW, EuclideanSpace(3), op)` → `ValueError: Cannot move a vector from MassWeightedSpace(EuclideanSpace(dim=3)) to EuclideanSpace(dim=3)`. `EuclideanSpace(n)` is minted freely (`from_vectors`, `coordinate_projection`), so this bites in practice. Fix: `other == self._base` (and `self == other` in the `HilbertSpace` default, spaces.py:99). `_relating_mass` already uses `==` (operators.py:91).
3. **`JacobiPreconditioner` docstring claims a cost the code does not deliver.** preconditioners.py:84-88: "an operator that knows its own diagonal — diagonal, matrix-backed, *or a sum or scaling of those* — gives it up for nothing." prof5, dim 2000: `M + 0.5 I` → 2000 applications, 1914 ms; `2*M` → 2000 applications, 1855 ms; `TikhonovNormalOperator` (model space, matrix-backed A) → 2000 forward applications, 283 ms, against 3 ms for `samples=20`. This is the justification given for changing v1's default (`num_samples=20`, preconditioners.py:41) to exact.
4. **`DiagonalLinearOperator` on a non-diagonal metric refuses its own calculus** (A Must-4, unfixed): `DiagonalLinearOperator(make_dense_metric_space(3), [1,2,3]).sqrt` → `ValueError: A square root requires POSITIVE_SEMIDEFINITE; this operator has NONE` (diagonal.py:201, 218, 286); `log_determinant` likewise. `_rebuild` (:128) drops caller traits: `(2*DiagonalLinearOperator(D3, d, traits=SELF_ADJOINT)).traits == NONE`.
5. **`BandedPreconditioner`/`BlockPreconditioner` claim `SELF_ADJOINT` on any operator** (preconditioners.py:249, 402), including `form="components"` on a non-self-adjoint one: `check_traits(BandedPreconditioner(1, form="components")(A))` fails on `make_dense_metric_space(3)` and `(30)` (metric_checks).
6. `assembled()` docstring (operators.py:844-847) still says the metric enters "once, inside the adjoint"; the Galerkin-stored forward action applies `solve_gram` per call (:1434-1436). Measured cost in §1 row A Must-3.
7. Docstring/parameter mismatches: `from_tensor_product` (operators.py:1062-1067), `from_derivative_components` (:1946), `multiplication_operator` (spaces.py:541-547: no adjoint is supplied; `.adjoint(y)` raises).

## 3. Optimisations, ranked (gain × confidence)

Baselines: Euclidean CG at 2000 is at parity with scipy (v2 20 it 16.0 ms, scipy 20 it 16.1 ms, the 20 matvecs alone 15.8 ms — prof4); composition nodes add 0.1–0.2 µs per factor per application, node construction ≈ 10 µs, `close()` 5 µs (prof7) — none of that is worth touching. Sphere lmax 128 (dim 16641): one transform ≈ 3.6 ms; lmax 64: 0.5 ms.

1. **Inner products on spectral spaces cost two transforms; norms too.** `DiagonalMetricSpace.inner_product` (spaces.py:772-776) analyses both arguments, so `norm(x)` = 2 analyses of the same vector (prof6: `norm` 2, `inner_product` 2; v1 did the same, hilbert_space.py:618-621). CG on the sphere with a diagonal operator: 7.4 analyses + 1.1 syntheses per iteration (prof6), of which the operator is 1+1 and the vector algebra 6.4. (a) Override `squared_norm` on `CoordinateSpace` to transform once: 2→1 per norm. (b) In `CGSolver._solve` (solvers.py:750, 756) `rz_next = inner_product(r, z)` recomputes `‖r‖²` when `z is r`: reuse `residual**2`. Together 7→4 analyses/it on the sphere (≈43 % of the vector-algebra cost); on the 2000-dim dense-metric CG the three Gram applications are 63 of 95 ms, so (b) alone saves ≈21 ms (22 %). (c) The real fix is to run the Krylov loop **in coefficients** when the space is a `CoordinateSpace`: prototype (prof6b/6c, same operator wrapped as `to_components∘A∘from_components` on a weighted array space) — diagonal operator 237.5 ms → 0.4 ms (×600); grid operator `M*M + I` 8.2 s → 5.8 s (10+4 → 5+5 transforms/it, the wrapper still pays 2); model-space normal `Q⁻¹ + A*A` (500 points, lmax 64) 1636 → 1277 ms, 9+2 → 4+3 transforms/it, of which `A`/`A*`/`Q⁻¹` are 1, 2+1, 1+1 — with components-native point evaluation (Y area) that would be ≈1 transform/it, i.e. ≈10×. Risk: low — same algorithm; residual norms identical since the components inner product carries `G`; preconditioner operators need the same wrapping. Confidence: high (measured).
2. **`orthonormal_basis`/`gram_schmidt` on a spectral space are O(k²) transforms.** `_orthogonalise_against` (spaces.py:241-263) takes `inner_product` per pair: 30 vectors at lmax 128 = 990 analyses, 3494 ms; prototype doing the same MGS (same reorthogonalisation rule) on a components array: 30 analyses + 30 syntheses, 204 ms (×17), agreeing to 1e-8 (prof6b). Downstream: `random_eig(D, rank=20)` on the sphere = 4890 analyses, **16.4 s**; `SpectralPreconditioner(rank=20)` build 5130 analyses (prof6c); randomised.py:95-98, 151, 180, 388, 449 all go through this. Fix: `CoordinateSpace.orthonormal_basis/gram_schmidt` in components (`apply_gram`-weighted dots), returning `from_components`. Est. `random_eig` 16 s → ≈1 s. Risk: low. v1 did the same as v2 (low_rank.py:658 `gram_schmidt`), so this is an optimisation, not a regression.
3. **`from_vectors` re-transforms its stored vectors on every adjoint.** operators.py:1041-1042: rank 20 on the sphere → 40 analyses per `adjoint(y)` (prof6), and `LowRankEig`/`SpectralPreconditioner.apply` = 40 analyses + 1 synthesis per application (≈145 ms at lmax 128 vs 3.6 ms with cached components). Fix: when the codomain is a `CoordinateSpace`, store `V_c` once (r analyses at build) and use `value = from_components(V_cᵀc)`, `adjoint = V_c · apply_gram(to_components(y))`: 1 transform each way; keep the coordinate-free path otherwise. Cost r×n floats (rank 100 at lmax 256: 53 MB). Risk: low.
4. **Expression nodes have no `matrix()` fast paths** (prof3, dim 2000, Euclid / dense metric): `(A@B).matrix()` 3356/3492 ms vs `M1@M2` 286/356; `(A+B)` 3461/4404 vs 3/4; `(2A)` 1427/1722 vs 2; `A.adjoint.matrix()` 1357/**23 270** vs 716/819 (Galerkin(A*) = Galerkin(A)ᵀ exactly; components(A*) = `G_X⁻¹MᵀG_Y`, one multi-RHS solve); `D.matrix()` 11/12 vs 0; `LU(A).matrix()` 2005/2714 vs 424/365 (`lu_solve(factor, I)`). Consequence for solvers: `CholeskySolver()(M + 0.5 I)` — the `DampedSolves` shape without `assemble` — 1602 ms vs 78 ms stored (Euclid), **25 078 ms vs 88 ms** on the dense metric (the Galerkin-stored `_value` pays a `solve_gram` per column *and* the post loop). Fix: a `_known_matrix(form)` hook returning `None` by default, implemented by `MatrixLinearOperator`, `DiagonalLinearOperator`, `_Identity/_Zero`, `_Scaled`, `_Sum` (all terms known, converted to one form via `_in_form`), `_Composition` (all factors known), `_Adjoint`, `InverseOperator` (direct solvers), block operators (`np.block`/`block_diag`, the v1 fast paths). Risk: moderate only in the form bookkeeping; each identity above was checked numerically in prof3 (`agree=True`).
5. **`matrix()` post-processing loops** (operators.py:739-745, 761-765; `_in_form` 1454-1464): on a dense Gram the per-column `apply_gram` doubles the extraction (galerkin/columns 2766 ms = 1339 raw + 1342 loop, vs 252 ms vectorised → ≈43 % of the call), and the per-column `solve_gram` dominates it (components/rows 16 240 ms, loop 12 800 vs 303 vectorised → ≈79 %); `_in_form` 1354 → 254 ms. On diagonal/Euclidean metrics the loops are 11 and 6 ms of ≈1400 (<1 %). Fix: `apply_gram_matrix(M)`/`solve_gram_matrix(M)` hooks (loop default; broadcast on `DiagonalMetricSpace` — note `values * M` is *wrong* on a matrix; `G @ M` / factorised multi-RHS on MFEM and `AdaptedSpace`). Gain only on dense-Gram spaces (MFEM backend, `compat.AdaptedSpace` over v1 mass-weighted spaces). Confidence high.
6. **LU double factorisation** (§2 bug 1): build 91 → 47 ms at 1500, O(n³). Trivial fix.
7. **O(1) diagonals for nodes, and Jacobi.** Add `_known_diagonals(offsets, form)` alongside item 4 (`_Sum` sums, `_Scaled` scales, `_Adjoint` transposes offsets in Galerkin form). Measured: Jacobi on `M + 0.5 I` 1914 ms → read (0.6 ms on the bare matrix); on `TikhonovNormalOperator` 283 ms exact vs 3 ms `samples=20` — the composition `A*A` cannot be read, so either the docstring changes or the default does (§4).
8. **Block operators allocate and transform for nothing on field spaces.** `BlockOperator._value` (direct_sum.py:416-424) starts each row from `codomain.zero()` and `axpy`s every block including `_Zero`; `Column._adjoint_value` (:537-542) and `Row._value` (:585-590) likewise. `CoordinateSpace.zero()` is a synthesis on the sphere (prof6: `zero()` = 1 synthesis; `_Zero._value` another). `[[I,0],[I,I]]` on two spheres costs 3 syntheses per application, `[I;I]` adjoint 1, all avoidable (skip `_Zero`, start from `copy(first)` — copy is a grid copy, cheaper than a synthesis; `_Identity` returns its input, so the copy is needed). At lmax 256 ≈ 45 ms per application of the pyslfp-shaped joint operator. Also `Sphere` should override `zero()` (Y area). Confidence high, gain modest.
9. **`NormalDiagonalPreconditioner` inner product in components.** inference/preconditioners.py:144-146 `inner_product(pulled, Q pulled)` = Q (1+1) + inner product (2) transforms per data index on the sphere; with `Q` a `DiagonalLinearOperator` compute `c = to_components(pulled); c · apply_gram(d ⊙ c)` = 1. Measured 500 points, lmax 64: 2013 → 1523 ms (25 %), 6 → 3 transforms per index; the remaining 3 are `A.adjoint` (2 analyses + 1 synthesis for point evaluation — Y area). At pyslfp scale (10⁴–10⁵ points, lmax 256) both are minutes; `blocks=` is the real lever.
10. `MatrixLinearOperator.diagonals` is a Python double loop (operators.py:1529-1536): 6.6 ms vs 0.07 ms with `np.diagonal` at 2000×21 offsets; O(offsets·dim) Python. `DiagonalLinearOperator.matrix()` has no override: 11 ms at 2000 Euclid, 2·dim transforms on a sphere (`check_traits` INVERTIBLE path, testing.py:556). Both trivial.

Measured and **not** worth it (<10 %): `HilbertSpace.add` = copy+axpy is 3–9× `x+y` at n ≥ 2e5 (408 vs 45 µs) but ≤1 % of any solve at those sizes; `_Sum`/`_Composition` overhead ≈ raw; DirectSum tuple overhead ≈ 2 µs/block/op (20×100 blocks: 175 µs/it, all Python, but blocks of 1000 make it <5 %); `SolveResult` allocation; FCG/MINRES temporaries; `DampedSolves` inverse cache (no multiplier is probed twice in a sweep).

## 4. Open questions for the user

1. **Krylov in coefficient space** (item 1c): make `IterativeSolver` switch representation automatically on a `CoordinateSpace`, or add an explicit wrapper? The automatic route changes nothing numerically but wraps user preconditioner operators and `x0`; it also makes a components-native action on point-evaluation operators (Y area) worth adding, which is where the remaining 5× is.
2. **Jacobi default**: keep exact (dim forward applications on any composed operator — unusable with a PDE forward, and the docstring's reason is false) or restore v1's `samples=20`? A middle course is exact when `_known_diagonals` answers and `samples=20` otherwise, with a warning.
3. **`assembled()` form**: components (no `solve_gram` per application for self-adjoint operators; 3.4× cheaper CG on a dense metric) and let `DirectSolver` convert once via `_in_form`, or keep Galerkin for the symmetric matrix?
4. **`from_vectors` caching components** costs r×n memory by default; acceptable, or opt-in?
5. **`make_dense_metric_space(dim)`**: fix the fixture's conditioning (e.g. `I + 0.3·tril/√dim`, or an orthogonal conjugation) so the metric rule can be applied at realistic sizes? Every dim > 60 use is testing roundoff.
