## 2. Bugs and regressions found now

**Verified**

- **B1. `ProximalBundleMethod` reports convergence 2× off the true support value on a tight-noise, over-determined problem**, and `DualFeasibleProperty.support_values` takes it as the answer. Reproduction (`p2c_osqp_simplex.py`, `p2_bundle.setting(300, 2000)`: dense-metric model space dim 300 (root `I + 0.3/√n·tril(N)`), Euclidean data dim 2000, prior `Ball(3)`, noise `Ball(1.2·‖noise‖)`, direction `e_0`): true value **0.181539** (SLSQP feasible point with the noise constraint active, slack −9e-15; `ChambollePockSolver` at 20 000 iterations agrees to 1e-6). `ProximalBundleMethod(tolerance=1e-10, iterations=300)` (the `DualFeasibleProperty` default, backus.py:1026): value **0.362105**, `converged=False`; with the subproblem solved by OSQP instead: value 0.362105, `converged=True`, gap 1e-10, 140 iterations; at 3000 iterations and capacity 100: 0.1906, gap 2e-12, still `converged=False`. The docstring (convex.py:866–876) says the gap is not a bound; here it is not even indicative, and the result is a support value 100 % too large presented without warning. Cross-area, same problem: `route="kkt"` −0.043662 (below a feasible value: wrong, the documented multiplier saturation), `route="primal"` 0.227532 at its default 1000 iterations (unconverged, not flagged), `route="smoothed"` 0.324664. At (300 model, 60 data) all five agree to 1e-8 (`p6_routes.py` on Euclidean, weighted and dense-metric spaces). The CURRENT_STATE.md §4 table ("agreement 1.7e-8") holds only for a loose noise set.
- **B2. `LevelBundleMethod.minimise` misreports `iterations`** after the `break` at convex.py:1443–1447: the tail return (1453–1456) passes `self._iterations`. `p2b_level_debug.py`: `evaluations=1, iterations=100, message="the master problem could not be solved"`. Same shape as the trust-region item the appendix flagged. Cause of the failure itself: on a first cut with `|g| = 1.7e7` OSQP returns `dual infeasible` for the proximal fallback master while Clarabel solves it — backend-dependent, and the method then gives up on iteration 1 with `gap=inf`.
- **B3. `LevelBundleMethod` does not converge where the proximal method does, and is 10–60× slower** (`p2.out`): (300, 60): 43.65 s, 200 iterations, `converged=False`, value 43.231 (proximal: 61 iterations, 1.19 s, 43.2308, correct to 1e-8); 589 OSQP solves ≈ 3 per iteration (level infeasible → two `alpha` retries → fallback). (300, 2000): 138 s for 200 iterations, 0.58 s/iteration in `linprog` on 2001 variables, value 1.93 vs truth 0.18. The certified gap it is meant to provide never closes.
- **B4. `make_dense_metric_space(dim)` (tests/conftest.py:101–103) is not positive definite above dim ≈ 300**: cond 5.8e5 at 100, 5.7e13 at 300, `LinAlgError` at 500. The metric-rule fixture cannot be used at realistic sizes, and at 300 it is numerically meaningless: on a *feasible* problem (min-norm fit norm 0.15 < 3) the four routes returned 708 / 0.85 / −1756 / 1729. Scaling the off-diagonal by `1/√dim` (as `p1`/`p2` do) gives cond 3.4 at 300 and 3000.
- **B5. `ArmijoLineSearch` still reports `evaluations=max_backtracks`** on the `min_step` exit (line_search.py:136–138); N Should-14 left this one.
- **B6. Documentation false claims.** CURRENT_STATE.md:99 "`ProximalBundleMethod` / `LevelBundleMethod` — the subproblem is dense in the number of cuts": the level master is dense in the **data dimension + 1** (convex.py:1349–1351, `np.zeros((size+1, size+1))`) and its LP has `dim+1` variables (1319–1332); measured 401 MB per master call at 5000 data (O4). V1_CATALOGUE.md:207 `Cut, Bundle` "Ported" — no such classes (cuts are tuples); :208 names dead `_ConvexResult`; :214 `best_available_qp_solver` "Planned" one row below where it is ported.
- **B7. `lanczos_tridiagonalise` still lacks `breakdown_tol`** (p5 signature) — Should-11's second half.

**Unverified suspicions**

- `ProximalBundleMethod._gram` keys its cache on `id(gradient)` (convex.py:1018). Safe as written because every current cut was created while the dropped one was alive and the cache is rebuilt before any new cut is made; fragile against any reordering of `append`/`pop`/`_solve_model`. A counter key costs nothing.
- `PrimalKKTSolver._kernel` (convex.py:1892–1894) forms an `n×n` matrix and `np.linalg.solve`s it on every `fsolve` residual evaluation (O(n³) each, 20–50 per direction). A generalised eigendecomposition of `(Γ, V⁻¹)` once per solver would make each solve O(n²). Not measured.
- `monotone_root`'s downward walk warm-starts from the solution at the *largest* multiplier reached (root_find.py:182–191, 258–274) — appendix §2.7, unchanged.

## 3. Optimisations, ranked (gain × confidence)

**O1. Inner products through `to_components` inside the numerics loops — the dominant cost on every non-orthonormal space.** `DiagonalMetricSpace.inner_product` (spaces.py:772–776) and `CoordinateSpace.inner_product` (409–412) transform *both* arguments; `Sphere.to_components` is an `SHExpandDH` (sphere.py:386–411). One inner product: **1.42 ms at lmax 64, 10.9 ms at 128, 72.8 ms at 256** (`p3_sphere.py`), against 0.008/0.04/0.18 ms for an `axpy`. Every routine here does O(k²) of them on k vectors that never change: Lanczos reorthogonalisation (functional_calculus.py:139–140), `_orthogonalise_against` (spaces.py:241–262), `orthonormal_basis`, `from_vectors.adjoint` (operators.py:1042–1043), `random_eig`'s projection (randomised.py:387–389), the bundle Gram. Measured at lmax 64: `apply_operator_function`, 30 steps: **1047 `SHExpandDH`, 60 of them the operator's**, 1.10 s against 0.35 s for the 30 bare applications (68 % overhead); `orthonormal_basis(50)`: 2650 transforms, 1.91 s; `random_eig(rank=20)`: 5794 transforms for 120 applications, 4.63 s; `log_determinant(samples=10)`: 2320 transforms, 1.74 s. On a 3000-dim dense-metric space (`p1_random_eig.py`) `random_eig(rank=50)`: **12 831 Gram applications = 40.7 of 42 s**, operator applications 0.65 s. Prototypes: Lanczos keeping the basis in components (`p3b_lanczos_proto.py`, one analysis per step, MGS on arrays with `metric_values`, one synthesis at the end): 1146 → 152 transforms, **0.68 → 0.22 s (3.1×) at lmax 64, 4.10 → 1.09 s (3.7×) at 128**, result identical to 1e-14; the remaining cost is the operator itself. Component MGS for `orthonormal_basis(50)`: 100 transforms, **1.91 → 0.10 s (19×)**. Cholesky-QR (twice) in components for `random_eig` on the dense-metric 3000: **38–46 s → 1.5–1.7 s (23–30×)**, eigenvalues to 3e-14. Extrapolated to lmax 256 with the 72.8 ms inner product: one `operator_sqrt` application at the default `max_iterations=50` spends ~1250 reorthogonalisation inner products ≈ **90 s** where the 50 applications of a diagonal-plus-low-rank covariance cost a few seconds; `log_determinant` at its defaults (100 probes × 40 steps) is hours of transforms. Fix: a `CoordinateSpace` path in `_orthogonalise_against`/`orthonormal_basis`/`gram_schmidt` and in `iter_lanczos_tridiagonalise` that converts once, works on `(dim, k)` arrays with `apply_gram`, and converts back; `from_vectors` storing components when the codomain has them; `random_eig`/`random_svd` Gram matrices as `Cᵀ (G C)`. Coordinate-free spaces keep the current code. Risk: low (pure refactor; the metric enters only through `apply_gram`; test on `make_dense_metric_space` once B4 is fixed). Confidence: high (measured on three space types).

**O2. Block application for matrix-backed operators.** `random_range`/`_power_iterate`/`random_eig` apply the operator one probe at a time (randomised.py:80, 95, 98, 386). On `EuclideanSpace(3000)` with a dense `MatrixLinearOperator`, `random_eig(rank=50)`: 240 mat-vecs = **0.72 of 0.80 s**; four GEMMs in the prototype: **0.16 s (4.6–5.0×)**. Needs an `apply_block(vectors)` hook on `LinearOperator` (default: the loop) overridden by `MatrixLinearOperator`, `DiagonalLinearOperator`, `from_vectors`, sums/compositions — and it is where D-6's `n_jobs` for `random_range`/`random_diagonal` belongs (parallel.md R-list). Risk: low. Confidence: high for dense/sparse matrices; no gain for transform-based operators unless pyshtools batching is added.

**O3. `ProximalBundleMethod` subproblem: FISTA on a Gram matrix of condition 1e13–1e23.** Measured (`p2.out`, (300, 60), 6 directions): 5.83 s total, **5.44 s (93 %) in `_minimise_on_simplex`**, 331 calls, 253 361 FISTA iterations (765 of the 1000 cap on average); oracle, Gram and vector algebra < 0.4 s. On 20 synthetic 40-cut bundles with cond(Q) ≈ 3e13 (`p7`, second script): FISTA 13.8 ms/call, KKT residual median 2.6e-5, max 2.2e-4; **OSQP with polishing at `eps=1e-6`: 0.9 ms/call, residual 4e-16** (1e-8: 1.3 ms, same); Clarabel 0.7 ms but residual 4e-3. In the full run (`p2c_osqp_simplex.py`, OSQP at 1e-10): 3.86 → 2.70 s and 61 → 42 outer iterations at capacity 40, accuracy vs KKT 8e-9 → 1e-9; at capacity 100 and 1e-10 OSQP cost 55 ms/call, so the tolerance must be 1e-6…1e-8, not 1e-10. A warm start from the previous weights was tried and **gives nothing** (957 vs 976 FISTA iterations on the near-parallel bundles): the cap is hit either way. Recipe in `rereview_N_recipes.md` §3. Expected: ≈ 10× on the subproblem, ≈ 2–4× on a `support_values` run. Mag's method — see §4.

**O4. `LevelBundleMethod` master problem dense in the data dimension.** `_master` (convex.py:1336–1369) builds `P = diag(I_n, 0)` as a dense `(n+1)²` array and hands it, and `k` dense rows, to a backend that densifies again (`_validate`, quadratic_programming.py:134); `_lower_bound` solves an LP in `n+1` variables. Measured per call: n=500 61 ms / 5 MB, n=2000 30 ms / 64 MB, **n=5000 125 ms / 401 MB**; at 10⁴ data points 1.6 GB per call, at pyslfp's 10⁵ impossible. The LP costs 0.58 s per iteration at n=2000. The Lagrangian dual of the level QP is a `k`-variable non-negative QP on the cuts' Gram matrix (which `ProximalBundleMethod._gram` already keeps incrementally), solution `x = c − Σ λ_j g_j`: **2 ms at n=5000 via OSQP**, Gram build included. v1 (convex_optimisation.py:1198, 1244) also used `np.eye(d)`, so this is parity, not a regression. Also `_cut_rows` re-transforms every cut on each of its 2–4 calls per iteration; cache the components with the cut. Risk: medium (Mag's method; the LP bound must stay). Confidence: high on cost, but B3 says the method's convergence is the bigger problem.

**O5. `monotone_root` evaluation count.** Geometric bisection to `rtol=1e-6` after decade bracketing: **23–28 solves per root** for `initial` at 1, 1e-3, 1e3 (`p4_root.py`); the same bracketing followed by Brent's method in `log t`: **10–13 solves**, same root to 6 figures. Each solve is a CG or direct solve of the damped normal operator in `DiscrepancyPrinciple`/`MinimumNorm.for_data` — at lmax 256 the whole cost of a discrepancy sweep. v1 (linear_optimisation.py:896–948) bisected arithmetically with a warm start, so v2 is at parity. Risk: low (keep the geometric bracketing and the warm start; Brent needs only a 1-D root on a monotone function). Confidence: high.

**O6. Wasted evaluations in the convex methods.** `SubgradientDescent._minimise` (convex.py:538, 545) evaluates `f(x)` twice per iteration and uses the first only for `rule="polyak"`: 50 % of value evaluations wasted on the default rule (p5: 3 value calls for 2 iterations). `ProximalGradient._run` (676, 703) evaluates `total(x)` for the history and `smooth(trial)` per backtrack without counting: 9 value + 4 derivative calls for 2 iterations reported as `evaluations=3`. Small absolute cost; counts are wrong.

**O7. Below the 10 % bar, noted only:** `log_determinant` goes through `apply_operator_function` + `inner_product` (functional_calculus.py:609–615) instead of `operator_quadratic_form`, spending k `axpy`s and one inner product per probe (≈5 % after O1); `random_cholesky` (randomised.py:518–523) re-forms the eigenvectors through `factor(e_i)` (k² `axpy`s, 0.02 s at k=50); `iter_lanczos_tridiagonalise` copies the basis list on every yield (142); `random_eig` re-applies the operator to the basis after `_power_iterate` already applied it to a basis that was then re-orthonormalised (unavoidable without returning both).

## 4. Open questions for the user

1. **May the numerics take a component path on a `CoordinateSpace`?** O1 and O2 are the whole of the measured gain (3–30×) and both mean `orthonormal_basis`, Lanczos, `from_vectors` and the randomised routines doing arithmetic on `(dim, k)` arrays whenever `to_components` exists, keeping the coordinate-free code as the fallback. `random_diagonal` already sets that precedent; DESIGN's "coordinate-free" principle would then read "coordinate-free when it must be".
2. **B1 changes what `DualFeasibleProperty` should do by default.** On a tight noise set the proximal dual's gap says "converged" at 2× the answer, the level method does not converge at all, KKT and the default primal are also wrong, and only Chambolle–Pock with 20× its default iterations reaches the truth. Should `support_values` cross-check routes, run the primal to a feasibility tolerance rather than an iteration cap, or refuse to report a dual value without the level method's certified gap? This touches Mag's API (D-13), as do O3 and O4.
3. **Fixture:** may `make_dense_metric_space` scale its off-diagonal by `1/√dim` (B4)? Every dense-metric test above dim 300 depends on it.
