# Review of the pygeoinf2 algebra layer (v1 → v2)

> **Note (2026-08-27):** the decisions recorded in `pygeoinf2/REVIEW.md` §11 (D-1 … D-13) override the Must/Should/Consider ranking below wherever they conflict — in particular D-1 (sphere vectors are `SHGrid`, `sampling=1` default), D-2 (points in `(lat, lon)` degrees), D-3 (per-geometry submodules with `Lebesgue`/`Sobolev` subclasses), D-4 (`from_matrix(..., form=)`), D-6 (parallel hooks around operators), D-12 (path *integral* operator), D-13 (convex solvers restored).

Scope read: v1 `hilbert_space.py`, `linear_operators.py`, `linear_forms.py`, `nonlinear_forms.py`, `nonlinear_operators.py`, `affine_operators.py`, `direct_sum.py`, `checks/*`, `parallel.py`; v2 `traits.py`, `algebra/{spaces,operators,nodes,linearisation,direct_sum,diagonal,__init__}.py`, `testing.py`, `compat.py`, `__init__.py`, `tests/test_code_practice.py`; DESIGN.md §1–5, §11.1–11.2, §11.6–11.7, §21.16; the catalogue rows for this area. Claims below marked *(verified)* were checked with a throwaway script against a dense, non-diagonal SPD Gram matrix on both domain and codomain.

## 1. Functionality retained / extended / lost

### Retained (renamed where noted)
`HilbertSpace` core (`dim, zero(), copy, inner_product, axpy, add, subtract, norm, squared_norm, gram_schmidt, mean`), `ax→scale_inplace`, `multiply→scale`, `sample_expectation→mean`; `CoordinateSpace` (`to/from_components, basis_vector, coordinate_inclusion/projection`); `OrthogonalHilbertSpace→DiagonalMetricSpace`, `OrthonormalHilbertSpace→OrthonormalSpace`, `EuclideanSpace`; `LinearOperator` (`adjoint, matrix, self_adjoint, identity, zero, from_tensor_product (rank-one only), from_vectors (see below)`), `with_dense_matrix→assembled`, `extract_diagonals→diagonals`; `NonLinearOperator→Operator`, `NonLinearForm→Functional`, `LinearForm→LinearFunctional`, `AffineOperator`; `HilbertSpaceDirectSum→DirectSum` (`subspace_projection→projection`, `subspace_inclusion→inclusion`), Block/Column/Row/BlockDiagonal operators; `checks/*→testing.check_*`; `HilbertModuleMixin→HilbertModule` (`vector_multiply→multiply`, `vector_sqrt→sqrt`).

### Extended (genuinely better)
Traits with closure and propagation (`traits.py`); memoised, involutive adjoint (operators.py:393-407) with structural palindrome recognition (nodes.py:245-263); `at()`/`Linearisation`/`QuadraticModel` sharing one evaluation; optional second derivatives; `white_noise` correct on non-orthonormal spaces (spaces.py:295-312, *verified*: component covariance = G⁻¹); `orthonormal_basis` with reorthogonalisation (spaces.py:178-216); `Reals` so functionals return floats; `DirectSum` labels and coordinate dispatch; nonlinear block operators with derivatives; `diagonals(probe="banded")`; `matrix(by=)` filling from the cheaper side; `from_derivative_callables`; sparse matrices accepted by the matrix constructors (operators.py:44-55); hashable spaces; `DiagonalLinearOperator` functional calculus with the correct non-self-adjointness on a non-diagonal metric (diagonal.py:68-84, 104-113, *verified*); `subgradient/prox/conjugate` hooks.

### Lost or not equivalent, despite catalogue status

1. **The functional algebra is not closed — Ported row for `NonLinearForm` is wrong** *(verified)*. `phi + psi`, `2*phi`, `phi @ F`, `phi @ A` all return `_OperatorSum/_OperatorScaled/_OperatorComposition` (nodes.py:297-419, 427-445), which are plain `Operator`s: `isinstance(_, Functional)` is False, there is no `.gradient`, `.hessian`, `.has_hessian`, and `at(x)` returns a `Linearisation`, not a `QuadraticModel`. v1's `NonLinearForm.__add__/__sub__/__mul__/__neg__/__matmul__` (nonlinear_forms.py:177-340) preserved gradient (and Hessian for `+,-,*`). DESIGN §5.5's table ("`phi @ A` → hessian `A* H A`", "`phi @ F` → hessian iff `F.has_second_derivative`") is not implemented. Concrete consequence: `numerics/optimisation.py:136-137` does `functional.at(x).gradient`, which raises `AttributeError` for any functional produced by the algebra (a misfit-plus-regulariser, `psi @ F`).
2. **`LinearFunctional` is not closed either** *(verified)*: `f + g → _Sum`, `2*f → _Scaled`, `f @ A → _Composition`; all lose `representer` and `derivative_components` (operators.py:1149-1182). And `LinearFunctional.from_callables` resolves by MRO to `LinearOperator.from_callables` (operators.py:652), returning `_CallableLinearOperator`, so there is **no way to build a `LinearFunctional` from a mapping** (v1 `LinearForm(domain, mapping=...)`, linear_forms.py:36-85).
3. **`AffineOperator @ AffineOperator` degrades** to `_OperatorComposition` *(verified)*; v1 kept it affine (affine_operators.py:139-149). operators.py:1278-1288 only handle a linear partner.
4. **Matrix-backed operators (catalogue "Ported")**: `from_component_matrix`/`from_derivative_matrix` return `_CallableLinearOperator` with the matrix captured in a closure (operators.py:800-802, 837-839). There is no attribute for the matrix; `A.matrix()` recomputes it by `dim` applications, `diagonals()` likewise; `assembled()` on an already-assembled operator re-extracts. v1 had O(1) fast paths (linear_operators.py:1105-1168, 1278-1339, 1515-1524). This is the "easy matrix-element access" the user asked about, and it is gone. `SparseMatrixLinearOperator`: the catalogue row says both "No sparse-backed operator in v2" and "Ported"; the truth is sparse input works in the constructors but `.matrix()` densifies via n matvecs and `sparse_array` access is gone; `symmetric_space/base.py:1176` `_weight_operator` is still private. `DiagonalSparseMatrixLinearOperator` (multi-offset banded storage, `from_operator(offsets)`, linear_operators.py:1342-1524) has no v2 counterpart; `DiagonalLinearOperator` is main-diagonal only.
5. **`from_formal_adjoint` / `MassWeightedHilbertSpace`** (catalogue "Ported"/"Subsumed"): only `symmetric_space.base.lift_formal_adjoint` exists, and it requires both spaces to be `SymmetricSpace` with `metric_values` (base.py:1248-1249). DESIGN §3.5's `MassWeightedSpace` and general `LinearOperator.from_formal_adjoint` were never built (11.1 defers them to M1; 11.2 does not mention them). There is no way to lift an operator onto an MFEM space, a full-Gram space, or a `DirectSum` of weighted spaces; v1's direct-sum recursion (linear_operators.py:159-183) is lost.
6. **`from_vectors` silently changed meaning** (catalogue "Ported"): v1 maps X→Rⁿ with `A(x)_i = ⟨v_i, x⟩` (linear_operators.py:294-338); v2 maps Rⁿ→Y, `c ↦ Σ c_i v_i` (operators.py:706-750) — the adjoint of the old. `from_vector`, `from_linear_form(s)` have no direct replacement; building the v1 object from matrix-free functionals requires `derivative_components` per row (a Gram apply each) and a dense matrix.
7. **`from_tensor_product` weighted sums** (`vector_pairs`, `weights`, `self_adjoint_from_tensor_product`, linear_operators.py:483-536) → rank-one only (operators.py:752-774). Catalogue "Ported" overstated.
8. **`matrix(dense=False)` SciPy `LinearOperator` wrapper with `matmat/rmatmat`** (linear_operators.py:600-665) gone; DESIGN 11.2 deferred it to M3 and M3 did not deliver (no `aslinearoperator`/`ScipyLinOp` anywhere in v2). Needed for `eigsh/svds/lobpcg` interop.
9. **`parallel.py`, `parallel=`, `n_jobs=`** dropped throughout (catalogue records this; user's note accepts it with reservations).
10. **Block operator `matrix()` fast paths** (v1 `_compute_dense_matrix` via `np.block/vstack/hstack/block_diag`, direct_sum.py:328-343, 422-430, 486-494, 539-547) gone; v2 block operators fall to the generic `dim` applications. `block(i, j)` on Column/Row/BlockDiagonal gone (use `.operators`); no bounds check on `BlockOperator.block` (direct_sum.py:383-385).
11. **In-place `LinearForm.__imul__/__iadd__`** (linear_forms.py:192-206) gone; v2 functionals are immutable. Acceptable, given representer caching, but not recorded.
12. **`EuclideanSpace.subspace_projection(indices)`** (hilbert_space.py:701-743) — absent from v2 and from the catalogue.
13. **`OrthogonalHilbertSpace.metric/inverse_metric`** (sparse diagonal matrices) gone; `DiagonalMetricSpace.gram_matrix()` falls to the dense column loop (spaces.py:331-339).
14. **Test-vector sampling from a `GaussianMeasure`** (`check(measure=...)`, checks/*.py) gone; `testing.check_*` accept only `rng`.
15. **`multiply` name hazard**: v1 `space.multiply(a, x)` was scalar multiplication; v2 `HilbertModule.multiply(x, y)` is the pointwise product (spaces.py:455) while scalar is `scale`. A v1-habit call `space.multiply(2.0, x)` on a `SymmetricSpace` (which is a `HilbertModule`, symmetric_space/base.py:48) does not error — it runs a pointwise product with a float through the grid transform. `test_code_practice.py:109-127` guards `scale` shadowing but not this.
16. `AffineOperator` no longer validates that `translation` lies in the codomain (v1 affine_operators.py:39-43); `is_element` is dropped by design, but nothing replaces the check.

## 2. Algorithmic performance

### Where v2 does more work

1. **Eager adjoint construction inside `@` triggers eager factorisation** *(verified)*. `_Composition.__init__` calls `factors[i].adjoint` for the first half of every *square* composition (nodes.py:240, 251) and `_block_traits` calls `.adjoint` on every block (direct_sum.py:343). For an `InverseOperator` from a `DirectSolver`, `_make_adjoint` (numerics/solvers.py:245-250) calls `solver(operator.adjoint)`, which extracts the adjoint's matrix by `dim` applications *and* factorises it (solvers.py:275-278). Measured: `Ainv @ Lin` performed a second LU at composition time; `Lin @ Ainv` did not. An `@` should never cost O(n³). Fix: the palindrome test must only consult adjoints that *already exist* (`factors[n-1-i].__dict__.get("_adjoint_cache") is factors[i]`, plus the `SELF_ADJOINT` trait for the middle), never construct them.
2. **Matrix retrieval is O(n·cost) instead of O(1)** *(verified*: n=1500, `matrix()` 0.10 s, `diagonals()` 0.19 s, `assembled()` 0.13 s, versus zero for a stored array; scales as n³). Every `DirectSolver` pays `dim` matvecs before factorising even when the operator was built from a matrix (solvers.py:277).
3. **`assembled()` picks the Galerkin form** (operators.py:594-599) so the assembled operator's *forward* action does a `solve_gram` per application (operators.py:828-831). On an MFEM codomain that is a mass solve per matvec that `from_component_matrix(self.matrix(form="components"))` would avoid; the docstring's "the metric still enters exactly once, inside the adjoint" is false.
4. **`matrix(form="galerkin", by="columns")`** post-processes with a per-column list comprehension and `np.column_stack` (operators.py:490-497; same at 510-513): `dim` Python calls and a second n×n allocation. For a diagonal metric this is one broadcast multiply.
5. **`HilbertSpace.add/subtract/scale` defaults** are `copy` + `axpy` (spaces.py:127-137): two allocations per term where v1's `x + y` was one. `_Sum._value` pays this per summand (nodes.py:189-193). `ArrayVectorMixin` should override `add/subtract/scale` with plain array arithmetic. (BLAS `daxpy` is *not* a win here — measured slower via SciPy's copying wrapper — so leave `axpy` as is.)
6. **`matrix(by="auto")` raises when the cheaper side has no adjoint** *(verified*: wide operator without adjoint → `NotImplementedError`). v1 guarded this (linear_operators.py:835-837). Fall back to columns.
7. `DiagonalMetricSpace` inherits the dense `gram_matrix()` loop and `_gram_cholesky` (spaces.py:309-339); `check_coordinates` then runs `eigvalsh` on an n×n matrix that is diag(g). Override with `np.diag`.
8. `BlockOperator._value` allocates `zero()` and runs `axpy` for `_Zero` blocks too (direct_sum.py:392-400); skip them.
9. `DirectSum` rebuilds a tuple per vector op (direct_sum.py:178-184); negligible. `_OperatorSum._linearise` builds a `_Sum` of derivatives per call; fine.
10. `testing.check_traits` computes `matrix_rank` twice (testing.py:509-512).

### Where v2 is better
Adjoint is memoised (v1 allocated a new `LinearOperator` on every `.adjoint` access, linear_operators.py:557-567); expression nodes add only ~0.2 µs per factor per application and no allocation *(verified)*; sums/compositions are flattened and scalings folded; `at()` removes v1's double evaluation in `NonLinearForm.__matmul__`; functionals are matrix-free (v1 `LinearForm(mapping=)` did `dim` evaluations in `__init__`); `zero()` is an explicit allocation; `white_noise` is correct; `DirectSum` slices are precomputed; `matrix(by=)` no longer detours through the dual; `diagonals(probe="banded")` is O(bandwidth) applications.

## 3. Code practice / quality

**Keyword-only args**: consistently applied and enforced. But factory argument *order* is inconsistent: `from_component_matrix(domain, codomain, M)`, `from_vectors(codomain, vectors)`, `from_tensor_product(u, v, *, domain, codomain)`, `from_representer(domain, v)`, `DiagonalLinearOperator(domain, values)`. Spaces-first everywhere would help.

**`from_derivative_matrix` naming**. The same matrix is called "galerkin" on extraction (`matrix(form="galerkin")`, `DirectSolver.form = "galerkin"`) and "derivative" on construction; `assembled()`'s docstring literally says "extracted in Galerkin form and handed back to `from_derivative_matrix`" (operators.py:586-588). "Derivative" is exact for a stack of functionals but meaningless for the covariances built with it in `examples/24_preconditioning.py:60-66` and `26_mixture.py:47-57`. Options, weighed:
- `from_galerkin_matrix` — consistent with the rest of the API and v1; downside is FEM jargon DESIGN §5.3 admits has lost its motivation.
- `from_matrix(domain, codomain, M, *, form: Literal["components","galerkin"])` with `form` **required** — DESIGN §5.3's objection was to `form="auto"` on construction, not to a required choice; gives an exact round trip with `matrix(form=)` and one constructor to document. **Recommended.**
- `from_weak_matrix` / `from_bilinear_form_matrix` — most precise (matrix of `(Ax, y)_Y`), but long.
- `from_dual_matrix` / `from_covector_rows` — accurate but reintroduces the dual vocabulary decision 1 removed.
Keep `LinearFunctional.from_derivative_components` as is; there "derivative" is exact.

**Duplication**: the four linear block classes each re-implement their nonlinear parent's `__init__` validation (direct_sum.py:465-477 vs 501-511; 536-549 vs 577-588; 609-617 vs 646-656; 363-366 vs 417-425). `LinearOperator.__add__/__mul__/__matmul__` (operators.py:605-645) duplicate `Operator`'s except for choosing `_Sum` over `make_sum`, which already dispatches on type.

**Reach-through**: `__dict__["_adjoint_cache"]` is written from nodes.py:110,206,285, direct_sum.py:444,523,596,664 and numerics/solvers.py:249 — a stringly-typed private protocol across three modules. Provide `LinearOperator._link_adjoint(other)`. `compat.py:46` imports private `_resolve_rng`.

**Imports**: cycles handled by 18 function-local imports in the algebra; fine. `LinearOperator.__init__` re-imports `close` on every construction (operators.py:364) though `traits` is already imported at the top. `testing.py:22-23` eagerly imports `geometry.convex` and `probability.base`, so importing the test helpers imports the whole package; make those lazy. `import pygeoinf2` is 0.25 s, dominated by scipy.

**Exports**: `HilbertModule` and `require_module` are in `spaces.__all__` but missing from `algebra/__init__.py` and `pygeoinf2/__init__.py`.

**Type hints**: `DirectSum[V](HilbertSpace[tuple])` declares `V` and never uses it (direct_sum.py:53); `_CoordinateDirectSum`, `BlockOperator`, `BlockLinearOperator`, `Column*`, `Row*`, `BlockDiagonal*` are unparameterised, so their `adjoint`/`derivative` types collapse to `Any`; `with_traits(...) -> Self` (operators.py:386) returns `_RetraitedOperator`, so `Self` is wrong; `LinearOperator.__mul__/__add__/__matmul__` are annotated `-> Operator` though they return `LinearOperator`. `Functional.__init__(domain, codomain=None)` exists only to survive the diamond MRO (operators.py:941-948); `LinearFunctional.__init__` could call `Operator.__init__` directly and drop it.

**Mutable state / memoisation**: `DiagonalLinearOperator.eigenvalues` and `DiagonalMetricSpace.metric_values` return the internal arrays (diagonal.py:91-93, spaces.py:510-513) — a caller can mutate them and desynchronise traits. `with_traits` returns `_RetraitedOperator` *(verified)*, losing the subclass (`eigenvalues`, `blocks`, `solve`) and the `_combine_*` specialisations. `Linearisation`/`QuadraticModel` are `@dataclass(frozen=True)` with default `eq=True`: `==` raises `ValueError` on array fields and `hash()` raises `TypeError` *(verified)*; use `eq=False`. Adjoint/representer/projection caches are correct single-threaded; the identity-based palindrome rule is **not thread-safe** — two threads first-touching `A.adjoint` concurrently get two `_Adjoint` objects, one escapes into a node, and the trait silently fails to fire (a CG solver then refuses the operator). Either guard with a lock or document single-threaded construction.

**Dunder dispatch**: `NotImplemented` is returned correctly for non-operators and non-numbers; no `__radd__`/`__rmatmul__` needed because both operands are always `Operator`s. `__eq__`/`__hash__` on operators is identity by design; consistent with `HilbertSpace._key` docstring.

**Error messages**: good and actionable in most places (`_CallableLinearOperator._adjoint_value`, `require_coordinates`, `DirectSum.index`, `LinearOperator.__init__`'s SELF_ADJOINT check). `BlockOperator.block(i, j)` has no bounds check; `_Sum`/`_Composition` constructors trust their callers.

**`test_code_practice.py`**: sound (docstring presence, kw-only optionals, annotations, vector-API shadowing). It cannot judge docstring *content*, which is where the gaps are (§4).

## 5. Correctness (metric-sensitive)

*(verified against dense non-diagonal Gram on both sides)*: `from_component_matrix` adjoint (`G_X⁻¹ Mᵀ G_Y`), `from_derivative_matrix` adjoint (`G_X⁻¹ Mᵀ`) and value (`G_Y⁻¹ M`), `coordinate_inclusion` adjoint (`G c_x`), `coordinate_projection` adjoint (`representer`), `matrix()` in all four `form × by` combinations, `diagonals()` in both forms and with padding aligned to `spdiags`, `DiagonalLinearOperator` adjoint `G⁻¹ D G` with traits `NONE`, `assembled()`, `white_noise` (component covariance `G⁻¹` to 1.2% at 4×10⁴ samples; default draw `L⁻ᵀξ` is the right one), `_CoordinateDirectSum.apply_gram/solve_gram` blockwise, `projection` adjoint, `P @ C @ P.adjoint` recognised as `SELF_ADJOINT|PSD`. `representer` and `derivative_components` are mutually consistent. MRO of `_CoordinateDirectSum` picks `DirectSum.inner_product` (sum) over `CoordinateSpace`'s, consistent with the blockwise Gram. Trait rules (`sum/scale/adjoint/compose/inverse/congruence/gramian`) are mathematically right and conservative.

Remaining concerns:
1. **`DiagonalLinearOperator.sqrt/inverse_sqrt/log/__pow__` gate on PSD/PD *traits*** (diagonal.py:179-215), which are never deduced on a non-diagonal metric. So `D.sqrt` refuses on an MFEM or full-Gram space even with all `d ≥ 0`, although `diag(√d)` is the square root of the linear map regardless of metric (functional calculus of a diagonalisable operator is basis-independent). Gate on the eigenvalues; derive traits separately.
2. **`_rebuild` drops user-supplied traits** (diagonal.py:126-128, 130-147): `DiagonalLinearOperator(X, d, traits=SELF_ADJOINT)` on a space whose non-diagonal `G` happens to commute with `D` (e.g. `G = f(D)`) loses the claim under `2*D`, `D + D`, `D.inverse`.
3. `AdaptedSpace.has_diagonal_metric` is a probabilistic probe (compat.py:248-263) feeding a *claim* (SELF_ADJOINT). Fine in practice; document that it is a probe.
4. Aliasing: `_Identity._value` returns `x` itself (nodes.py:57), `DirectSum.projection` returns the component object (direct_sum.py:216-217). `y = A(x); space.axpy(1, z, y)` mutates `x` when `A` is (or simplifies to) the identity. Same as v1, but undocumented; either document "operator outputs may alias inputs" or copy in `_Identity`.
5. `BlockLinearOperator` never deduces PSD/PD (direct_sum.py:332-345) — conservative, fine, but `[[I,0],[A,I]]`-style operators get `NONE`; acceptable.
6. Thread-safety of identity-based trait recognition (§3).

## Prioritised recommendations

### Must
1. **Close the functional algebra.** Add `_FunctionalSum/_FunctionalScaled/_FunctionalComposition` (subclasses of `Functional`) to nodes.py, returned by `make_sum/make_scaled/make_composition` when the result maps to `Reals`; propagate `gradient` (via the derivative's adjoint) and `hessian` per DESIGN §5.5 (`phi @ A` → `A.adjoint @ H @ A`; `phi @ F` → Gauss-Newton term plus `B(dx).adjoint(grad)` iff `F.has_second_derivative`). Make `_Sum/_Scaled/_Composition` with a `Reals` codomain return `LinearFunctional` subclasses (or move `representer`/`derivative_components` onto `LinearOperator` guarded by `codomain == REALS`). Add `LinearFunctional.from_callables(domain, value, /, *, representer=None, derivative_components=None, traits)`. Add tests: `(phi + psi).at(x).gradient`, `(psi @ F).hessian(x)`, `(f + g).representer`.
2. **Stop `_Composition`/`_block_traits` constructing adjoints.** In nodes.py:245-263 and direct_sum.py:332-345 replace `factors[i].adjoint is factors[j]` with a check that only reads existing links: `factors[j].__dict__.get("_adjoint_cache") is factors[i] or factors[i].__dict__.get("_adjoint_cache") is factors[j]`, and for the middle factor `Traits.SELF_ADJOINT & middle.traits`. Add a test that `solver(A) @ B` performs no second factorisation (count `_factorise` calls).
3. **Reinstate a matrix-backed operator class** (`MatrixLinearOperator(domain, codomain, matrix, *, form, traits)` holding dense *or* sparse) with `matrix`/`sparse` accessors, O(1) `matrix(form=)` when the stored form matches, O(1) `diagonals()`, `assembled()` returning `self`, `_combine_add/_combine_scale` staying in class, and `DirectSolver` reading the stored matrix. Have `from_component_matrix`/`from_derivative_matrix` return it. Make `assembled()` use the components form.
4. **Fix `DiagonalLinearOperator` gating and trait retention**: gate `sqrt/log/pow/inverse_sqrt` on eigenvalue signs; have `_rebuild` propagate the traits that survive (`SELF_ADJOINT` if the original claimed it; definiteness from the new values); make `with_traits` preserve the concrete class (e.g. `copy.copy(self)` with `_traits` replaced and `_adjoint_cache` cleared) instead of wrapping.
5. **Provide a general `MassWeightedSpace(base, mass, mass_solver)` and `LinearOperator.from_formal_adjoint(domain, codomain, operator, *, traits)`** per DESIGN §3.5, working on any `HilbertSpace` and on `DirectSum`s; keep `lift_formal_adjoint` as its diagonal fast path.
